# 06 · 风险预案与保底方案

## 风险应对升级（更具体的预案）

> 原则：先识别触发信号，再按「预防 + 止损」给预案；高优先级风险必须在对应 Phase 内闭环。

| 风险 | 触发信号 | 应对方案 | 优先级 |
| --- | --- | --- | --- |
| openpyxl 写文件损坏 | xlsx 打不开、读写抛 S001/S002 | 写前自动备份 `.bak`；单线程 + 内存锁；损坏时用备份恢复并定位写入点 | 高 |
| xlsx 并发写冲突 | 两个写操作同时报错或互相覆盖 | 原型限定单写入者；`storage.lock()` 内存锁；检测到并发写直接报错 | 中 |
| trace.jsonl 格式错误或缺人工干预 | `check_trace.py` 报错、平台解析失败 | 审计切面自动输出，禁止手动编辑；提交前跑 `check_trace.py`；人工干预走 `log_human_intervene` | 高 |
| 功能太多做不完 | 某 Phase 延误超过 1 天 | 按《01-项目定位与执行策略》2.4 的砍单优先级裁剪；9.18 前锁定权限+审计+规则三件套；启用保底方案 | 高 |
| 评审环境跑不起来 | clone 后安装失败、缺依赖/密钥 | 零外部 API 密钥、依赖锁定、`check_env.py` 自检、一键脚本装依赖 | 高 |
| GitHub 仓库 / Raw 链接不可访问 | 无痕模式打不开仓库或 Raw | 提前建仓多次推送；仓库 Public；Raw 链接无痕验证；仓库 URL 不带 `.git` | 中 |
| CLI 命令与规则联动不一致 | 验证命令跑不通、命令名混乱 | CLI 以 Phase4 定稿为准；命令集中在文档/常量；用集成测试覆盖 | 低 |

> 高优先级风险闭环时机：openpyxl 写损坏在 Phase0、trace 格式错误在 Phase2、功能做不完在 Phase3 前；中低优先级按需处理。

## 最低提交保底方案

> 触发条件：临近提交（如 9.18 后）发现无法完成全部 Phase 时，立即切换保底方案，优先保证可提交。

### 12.1 保底必须保留

| 保底项 | 最小可演示内容 |
| --- | --- |
| 组织权限 | members/teams/roles + 写前权限校验，readonly 写被拒（P001） |
| 审计日志 | audit_log 只追加 + 基础哈希链 |
| Rulesets 拦截 | 无审批 PR 合并被拦截（R001） |
| 最小工作流 | 一个 shell/python 步骤的 workflow，跑通并写 workflow_runs |
| 提交物 | 合法 trace.jsonl + README + 3-5 分钟 Demo 视频 |

### 12.2 保底链路（必须能跑通）

创建成员 → 创建 PR → 权限拦截 → Rulesets 阻止非法合并 → 运行一个工作流 → 审计 + trace 留存。

### 12.3 可砍掉的部分

- Webhook、定时触发器、Google Sheets、Streamlit WebUI；
- 完整 CLI 命令集、Mock Agent 自然语言层；
- 复杂规则（只保留「至少 1 审批人」和「required-check」两条）。

### 12.4 切换后的验证命令

```
python demo/init_seed.py
gx member add alice member
gx pr create --title "fallback demo"
gx pr merge 1                  # 预期被 R001 拦截（无审批人）
gx workflow run ci-check
python tools/check_trace.py
```

预期：链路可跑通，`audit_log` 与 `trace.jsonl` 均有记录。

> 原则：不追求功能多，追求链路完整、能跑通、可复现、符合大赛格式，比堆砌大量半完成功能得分更高。
