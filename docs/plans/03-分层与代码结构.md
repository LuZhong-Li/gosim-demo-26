# 03 · 分层与代码结构

## 项目分层与代码结构规范

> 目标：目录职责清晰、代码分层明确、问题定位快、修改影响范围小、排查有日志可追溯。不增加业务复杂度，只提升工程可维护性。

### 4.1 分层目录结构（按层分包，自下而上依赖）

**三层速查**：

| 层 | 目录 | 一句话职责 |
| --- | --- | --- |
| 底层 | `storage/`、`domain/` | 数据存取 + 纯数据模型，不依赖业务 |
| 中层 | `services/`、`core/` | 业务逻辑 + 门面编排 |
| 上层 | `api/`、`agent/` | 对外入口（CLI / 自然语言） |

### 4.2 分层设计原则与依赖矩阵

1. **自下而上依赖，禁止反向依赖**：上层（api/agent）→ 中层（services/core）→ 底层（storage/domain）；底层绝不依赖上层，改底层不会连锁影响上层。
2. **高内聚低耦合**：每个目录只干一件事，出权限问题只进 `services/perms`。
3. **统一门面入口**：上层所有操作走 `core/service_bus.py`，不直接调用零散服务；后续改内部实现，入口不变。

**允许 / 禁止 import 表**：

| 层 | 目录 | 可 import | 禁止 import |
| --- | --- | --- | --- |
| 底层 | `storage/`、`domain/` | 标准库、openpyxl、pydantic、`errors.py`、`constants.py` | `services/`、`core/`、`api/`、`agent/` |
| 中层 | `services/`、`core/` | `storage/`、`domain/`、`errors.py`、`constants.py`、`config.py` | `api/`、`agent/` |
| 上层 | `api/`、`agent/` | `core/service_bus.py`、`errors.py` | 直接调 `storage/`、`domain/`（必须走门面） |

**新增模块放置规则**：

1. 判断模块归属层：数据/模型 → 底层，业务 → 中层，入口 → 上层；
2. 中层业务模块放 `services/<name>/`，并在 `core/service_bus.py` 暴露入口；
3. 新模块只能 import 本层及以下层的目录，对照上面的依赖表检查；
4. 涉及新工作表时，先在 `constants.py` 注册表名，再建表。

### 4.4 代码结构规范

1. **统一错误体系**：`errors.py` 定义 `GXError(code, message, module, context)`；错误码前缀定位模块：

| 前缀 | 模块 | 示例 |
| --- | --- | --- |
| S | 存储 | `S001` 文件不存在、`S002` 工作表不存在 |
| P | 权限 | `P001` 权限拒绝 |
| R | 规则 | `R001` 规则违规 |
| A | 审计 | `A001` 审计写入失败 |
| W | 工作流 | `W001` 工作流运行错误 |
| B | 业务校验 | `B001` PR 状态/身份校验失败 |

```
class GXError(Exception):
    def __init__(self, code, message, module=None, context=None):
        self.code = code
        self.message = message
        self.module = module
        self.context = context or {}
        super().__init__(f"[{code}] {message}")
```

2. **常量与配置分离**：`constants.py` 存工作表名、角色、错误码；`config.py` 存路径、开关、日志级别、`DEBUG_MODE`，改参数不翻业务代码。
3. **日志分级 + Trace 联动**：`logging` 分 DEBUG/INFO/WARNING/ERROR 四级；ERROR 自动写入审计和 `trace.jsonl`。
4. **面向抽象编程**：只暴露 `BaseStorage` 接口，换 Google Sheets 只加实现类，上层不依赖 openpyxl。
5. **函数职责单一**：一个函数只做一件事，不超过 50 行。

**命名规范**：

- 文件：小写下划线，如 `service_bus.py`、`check_env.py`；
- 工作表名：小写 + 下划线，统一在 `constants.py` 定义（如 `workflow_runs`）；
- 函数：动词开头小写下划线，如 `check_permission`、`append_row`；
- 测试文件：`test_<模块>.py`，对应 `tests/unit` 或 `tests/integration`；
- 错误码：大写前缀 + 三位数字（S/P/R/A/W + 001）。

### 4.5 调试与排查便利化

- `config.py` 的 `DEBUG_MODE` 一键开启：打印调用链路、入参出参、数据快照、完整堆栈。
- 每个模块对应独立单元测试，改哪跑哪，不用跑完整 Demo。
- `audit_log` 保留 `before_snapshot/after_snapshot`，数据改错可直接回溯变更前的值。
- `trace.jsonl` 按时间顺序全链路可追溯：输入 → 接口 → 失败点 → 错误信息。

**按现象快速定位**：

| 现象 | 先查 |
| --- | --- |
| 写操作失败 | 权限（P001）→ 规则（R001）→ 存储锁 → 审计日志 |
| xlsx 打不开/损坏 | 存储错误码（S001/S002）→ 备份文件 |
| trace 不完整 | `tools/check_trace.py` + 拦截器日志 |
| 环境跑不起来 | `tools/check_env.py`（Python 版本、依赖） |
| 数据被改错 | `audit_log` 的 `before_snapshot` 回溯 |

**标准排查步骤**（遇到问题按顺序走）：

1. 开 `DEBUG_MODE=True` 复现，收集调用链路和报错栈；
2. 按上表「现象 → 先查」定位到模块；
3. 跑该模块对应单元测试确认修复；
4. 修复后检查 `audit_log` / `trace.jsonl` 是否留痕，再跑集成测试。

### 4.6 融入里程碑的工程规范任务

| 阶段 | 新增工程化任务 | 产出 | 落地检查 |
| --- | --- | --- | --- |
| Phase0 | 创建完整分层目录；编写 constants.py、config.py、errors.py；根 README + 模块 README 模板 | 规范骨架，后续按分层写 | 目录结构与 4.1 一致，三个根文件存在 |
| Phase1 | 按分层实现权限模块；编写对应单元测试 | 权限模块可独立测试排查 | `pytest tests/unit/test_perms.py` 通过 |
| Phase2 | 审计拦截器统一错误捕获；接入统一日志；trace 自动输出 | 报错自动留痕可追溯 | 故意触发一次错误，audit/trace 均有记录 |
| Phase3 | 工作流模块按接口规范实现；补充集成测试 | 改工作流不影响权限/审计 | `pytest tests/integration/test_workflow.py` 通过 |
| Phase4 | Agent 层只调用 core 门面；编写 AGENTS.md | 上层不碰底层逻辑 | 审查 api/agent 未直接 import storage/domain |
| Phase5 | 完善 docs/dev 文档；运行 check_trace.py / check_env.py 自检 | 交付前自检，减少低级错误 | 两个自检脚本全部通过 |
