# 01 · 项目定位与执行策略

## 项目定位与边界（细化）

### 1.1 一句话定位

**项目：GOSIM Create 2026 初赛作品**
名称：**GX-Sheet：基于电子表格模拟 GitHub 组织管控与自动化 Agent 原型**
🎯核心目标：实现 GitHub 四大能力的**核心语义原型验证**——把「组织权限、分支保护（Rulesets）、审计留痕、自动化工作流」这套管控链路架在普通电子表格上，用 Agent 自然语言作为交互入口；做**概念验证原型**，不是生产级完整复刻。

### 1.2 四大能力在本原型中的具体含义

| 能力 | 数据载体 | 核心行为 | 可验证点 |
| --- | --- | --- | --- |
| Actions 工作流 | `workflows` + `workflow_runs` | 行记录定义最小步骤，runner 顺序执行 shell/python/http；支持手动/数据变更/定时触发，Webhook 只预留字段 | `gx workflow run ci-check` 后 `workflow_runs` 新增记录 |
| 组织权限 | `members` / `teams` / `roles` | 写前按「主体 + 资源 + 操作」校验，拒绝即阻断并记审计 | readonly 用户写操作被拒（P001） |
| 审计留痕 | `audit_log` | 只追加、禁止修改历史行；每条带前一条 hash；统一走拦截器，绕过直接改 xlsx 视为违规 | 每次写操作后 `audit_log` 新增一行且带 `prev_hash` |
| Rulesets 规则 | `pull_requests` + `rulesets` | 模拟 PR-Review-Merge；初赛 2 条规则（审批 ≥ 1、required-check） | 无审批 PR 合并被拦截（R001） |

### 1.3 隐喻与工作表映射（唯一数据源）

**核心隐喻**：

| 隐喻 | 对应物 | 说明 |
| --- | --- | --- |
| Workbook | GitHub 组织 | 一个 xlsx 文件 |
| Sheet | 逻辑资源集合 / 仓库 | 8 张固定工作表 |
| 行记录 | 一条实体 | PR / Member / Workflow / WorkflowRun / AuditLog / RuleSet |
| Agent | 自然语言交互入口 | 把自然语言翻译成内部 API/CLI 调用 |

**8 张工作表职责**：

| 工作表 | 存什么 |
| --- | --- |
| `members` | 组织成员 |
| `teams` | 团队 |
| `roles` | 角色与权限配置 |
| `workflows` | 工作流定义 |
| `workflow_runs` | 工作流运行实例 |
| `pull_requests` | PR 模拟记录 |
| `audit_log` | 审计日志（只追加） |
| `rulesets` | 规则配置 |

> 电子表格是**唯一持久数据源**；进程内缓存仅加速读取，不作为权威源；所有变更必经 **权限 → 规则 → 业务 → 审计拦截器**。

### 1.4 目标演示链路（判定“做完了”）

一键 demo 跑通以下链路，且审计与 trace 都有记录：

| 步骤 | 动作 | 预期结果 | 留痕 |
| --- | --- | --- | --- |
| 1 | 创建成员 | `members` 新增一行 | audit_log + trace |
| 2 | 创建 PR | `pull_requests` 新增一条 | audit_log + trace |
| 3 | 权限拦截 | 无权限用户写操作被拒（P001） | audit_log（success=false）+ trace |
| 4 | Rulesets 阻止非法合并 | 缺审批或缺 check 时合并被拦（R001） | audit_log + trace |
| 5 | 运行 Workflow | `workflow_runs` 新增运行记录 | audit_log + trace（workflow_run） |
| 6 | 检查留痕 | `audit_log` 与 `trace.jsonl` 都有记录 | —— |

### 1.5 明确非目标（防范围膨胀）

| 不做的事 | 不做原因 / 去向 |
| --- | --- |
| 真实 Git 版本控制与提交 | 用表格字段模拟 PR/合并状态即可满足演示 |
| 生产级高并发多用户 | 面向单写入者演示场景 |
| GitHub Actions 完整 YAML 语法 | 只实现最小可演示步骤子集 |
| Webhook、分布式调度、Google Sheets 完整实现 | 归入 `FUTURE.md`，初赛不做 |
| 接入在线大模型 API | Agent 用 mock 字符串匹配模拟 |

### 1.6 大赛硬约束

| 约束 | 要求 | 落地方式 |
| --- | --- | --- |
| trace 自动输出 | 原生输出 `trace.jsonl`，每行一个 JSON | 审计拦截器切面自动追加写入 `demo/output/trace.jsonl` |
| 覆盖 5 种类型 | prompt / api_call / tool_call / workflow_run / human_intervene | 拦截器按场景写入对应 `type` |
| 禁止手动编辑 | trace 文件不能手工修改 | 只由程序写入；人工干预走 `log_human_intervene` |
| 硬性交付 | 提交时必须提供合法 trace 链接 | 提交前跑 `check_trace.py` 校验 |

> trace 不是事后补写，而是嵌入主链路自动生成。

## 执行策略优化：MVP 优先迭代，降低落地风险

### 2.1 总原则：小步快跑，每阶段都有可运行、可验证的产出

不追求一次性做完所有功能，按「最小骨架 → 核心能力 → 完整链路 → 交付打包」四步走，每一步结束都能跑通验证，避免堆到最后集中爆 bug。

### 2.2 四个 MVP 版本与验证点

| 版本 | 覆盖 Phase | 必须能跑通的验证点 |
| --- | --- | --- |
| 最小可用版 | Phase0-1 | 生成带全部工作表的 xlsx；`gx member add` / `gx member set-role` 能管理成员；readonly 用户写操作被拒绝 |
| 核心闭环版 | Phase2 | 无审批 PR 合并被拦截；`audit_log` 和 `trace.jsonl` 都有失败记录 |
| 功能完整版 | Phase3-4 | 自然语言触发工作流；`workflow_runs` 落表；工作流失败时 required-check 阻止 PR 合并 |
| 交付打包版 | Phase5 | 一键脚本跑通完整链路并自动生成 `trace.jsonl`，三项提交物就绪 |

### 2.3 每个阶段的完成定义（Definition of Done）

每结束一个阶段，都要同时满足：

1. 可运行：有对应 CLI 或脚本入口，能实际执行；
2. 可测试：`pytest` 有对应用例且全部通过；
3. 可演示：能单独演示该阶段产出，不依赖后续阶段；
4. 有留痕：写操作进入 `audit_log`，ERROR 自动写入 `trace.jsonl`。

### 2.4 迭代节奏与止损规则

| 情况 | 处理 |
| --- | --- |
| 每阶段工期 | 2-3 天，预留 0.5 天缓冲 |
| 提前完成 | 提前推进下一阶段 |
| 时间不足需砍功能 | 按固定优先级从后往前砍：权限 → 审计 → 规则 → 工作流 → Agent |
| 任一阶段结束 | 都可作为可提交版本，不追求「全部做完才提交」 |
