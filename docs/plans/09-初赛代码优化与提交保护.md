# 09 · 初赛代码优化与提交保护（提交前最后一轮）

> 触发时机：功能全部冻结、demo 视频录制之前。目标是在「不破坏初赛提交物」的前提下，
> 对源码做一轮纯工程化打磨：可读性、健壮性、CLI 体验、注释、文档。
> 业务逻辑缺陷（权限并集、PR 审批校验缺失等）**明确不在此轮修复**，见 9.4。
> 本版为细化增强版：在原有约束、安全优化、禁止改动清单基础上，新增前置检查、
> 风险预判、失败回滚、逐项判定标准与交付物核对清单，把“口头要求”变成可打勾流程。

## 9.1 背景与目标

- 评审会直接看源码仓库：清晰的注释、类型注解、错误处理、局限说明属于加分项；
- 演示视频与 `trace.jsonl` 是初赛提交物，任何改动如果导致事件序列变化，已录制的
  演示轨迹就会对不上，直接影响评审；
- 因此本轮只做「对外表现完全不变」的优化，所有可能改变行为的能力留到决赛迭代。

## 9.2 核心约束（红线，含违规后果）

| 约束 | 说明 | 违规后果 |
| --- | --- | --- |
| 不改 `run_demo.py` 输出事件序列 | 执行流程、事件顺序、`human_intervene` 一个都不能动 | trace 事件变化，视频与轨迹不匹配，初赛提交无效 |
| 不破坏 `trace.jsonl` schema | 8 个必填字段、5 种 type、字段名称全部保持原样 | `check_trace` 校验直接失败 |
| 不改 `init_seed.py` 种子数据 | 成员 id、初始团队、初始工作流保持原样 | 初始实体 ID 改变，整条事件链错乱 |
| `check_trace.py` 校验必须依然通过 | schema 校验规则不改，`human_intervene` 强制校验保留 | 不满足大赛校验要求 |
| 业务核心行为不变 | P001 权限拒绝、R001 规则拦截、`human_intervene` 事件、PR 流程逻辑不变 | demo 运行行为改变，与设计文档不一致 |

## 9.3 安全可优化清单

### 9.3.1 CLI 体验优化（`src/gx/api/cli.py`）

- `member list` / `team list` / `pr list` / `workflow list` 增加表头，不再裸输出数据；
- `[OK]` 输出绿色、Pxxx 错误输出红色；仅控制台显示，不写入 trace；
- help 文本补充角色枚举提示：`角色枚举 [owner/admin/member/readonly]`；
- 排查复制粘贴带入的非 ASCII 连字符（U+2011）：仓库当前未发现，无需替换；
  如后续发现，统一替换为标准 ASCII `-`，防止脚本匹配异常。

✅验收判定：执行 `python -m gx member list` 控制台可见表头；错误输出带颜色；
打开 `trace.jsonl`，确认没有新增/变更任何业务事件。

### 9.3.2 工程健壮性（不改变业务逻辑）

- 存储层读写 xlsx：增加 IO 异常捕获，给出友好报错（新增错误码 `S005`，
  文件不存在沿用已有 `S001`）；不修改写入内容与事件结构；
- trace 写入逻辑不动：已有 `OSError → A001` 防护，仅补注释说明；
- `tools/check_trace.py` 小优化（不改 schema 校验规则、不删 `human_intervene`
  强制校验）：
  - 打印当前 trace 共多少条事件；
  - 按 type 统计事件构成，并说明哪些来自脚本、哪些是 CLI/脚本共用链路
    （trace 未含来源字段，无法精确区分）；
  - 行数超过阈值（约 2 倍单次 demo 事件数）时输出警告：
    「检测 trace 存在历史残留事件，请执行 init_seed 重置」。

✅验收判定：正常 demo 运行输出 `[OK] trace 校验通过`；故意制造 xlsx 文件
不可读/不可写场景，可友好输出 S005；schema 与 `human_intervene` 强制校验不动。

### 9.3.3 注释、类型注解、常量（评审会看源码）

- 给核心 `service_bus.py`、`permission.py`、`trace.py`、`interceptor.py`、
  `xlsx.py` 补全函数 docstring，标明入参、返回值、P/R 错误码含义；
- 补齐缺失的 Python 类型提示，不改业务代码；
- 错误码抽成常量（值保持原样，trace/audit 输出字符串不变）：

```python
ERR_PERMISSION_DENIED = "P001"
ERR_RULE_PR_APPROVE = "R001"
ERR_STORAGE_IO = "S005"
```

✅验收判定：搜索源码，业务逻辑处不再硬编码 `"P001"`/`"R001"` 等错误码字符串
（统一从 `constants.py` 导入）；运行 demo，trace 输出的错误码字符串与旧版本完全一致。

### 9.3.4 目录与工程文档

- 新建 `docs/dev/limitation.md`：整理全部已知局限与待改进点（评审加分项）；
- 完善根目录 `README.md`：项目简介、大赛归属、环境准备、三步运行命令、
  初赛原型说明、已知局限、决赛迭代方向；
- `.gitignore` 确认：`.venv/`、`__pycache__`、`*.pyc` 已忽略；
  `demo/output/trace.jsonl`、`demo/seed-workbook.xlsx` **必须纳入版本跟踪**
  （`git check-ignore` 应返回非 0），并在 .gitignore 中显式声明不忽略。

✅验收判定：

```powershell
git check-ignore demo/output/trace.jsonl demo/seed-workbook.xlsx
```

两条命令均无输出（返回非 0），代表文件不会被 git 忽略。

### 9.3.5 日志输出细节

- 业务事件写入 trace 逻辑完全不动；
- 仅优化控制台 print 的显示（措辞/颜色），禁止新增、删除、修改任何 trace 追加事件。

✅验收判定：trace 事件数量与顺序和优化前一致（固定 10 条），仅控制台显示变化。

## 9.4 禁止改动（留给决赛迭代）

| 禁止项 | 原因 | 风险现象 |
| --- | --- | --- |
| 修改 `init_seed.py` 种子实体数据 | 会改变 trace 事件 | 成员 ID、实体 ID 变化，整条 trace 事件错位 |
| 修改 `run_demo.py` 流程、顺序、`human_intervene` | 演示视频轨迹对不上 | trace 事件数量、顺序改变 |
| 修复权限引擎“团队权限并集提权” | P001 行为变化 | 权限拦截不再触发或触发条件改变 |
| 修改 PR 审批逻辑（自审批、重复审批校验） | 业务行为改变 | PR 审批、合并行为与原 demo 不一致 |
| 增加成员、团队重名校验 | `run_demo` 依赖现有行为 | demo 脚本运行报错 |
| 修改 trace/审计事件数据结构、字段名称 | `check_trace` 校验直接失败 | 校验不通过 |
| 修改 `check_trace.py` schema 校验规则 | 大赛校验依赖 | 不符合提交校验标准 |

## 9.5 验证与提交流程

### 9.5.0 前置检查（代码优化完成后、第一笔提交前，必须全部打勾）

- [ ] `git status` 检查：工作区没有无关临时文件 / 未跟踪杂项
  （`.venv*`、`__pycache__`、`*.pyc` 已被 ignore）；
- [ ] 确认未改动《9.4 禁止改动》清单内文件逻辑：`init_seed.py` 零改动；
  `run_demo.py` 仅允许控制台展示层改动（颜色/文案），不允许流程、事件顺序、
  `human_intervene` 改动；
- [ ] `.gitignore` 校验：`git check-ignore demo/output/trace.jsonl
  demo/seed-workbook.xlsx` 两条均无输出（返回非 0）；
- [ ] 确认没有残留 `.venv.bak-*` 备份被误提交（`.gitignore` 已含 `.venv.bak-*/` 规则）。

### 9.5.1 代码优化阶段验证命令（第一阶段，仅代码与文档，不提交 trace）

```powershell
python demo/init_seed.py
python demo/run_demo.py
python tools/check_trace.py
python tools/check_env.py
pytest -q
```

✅判定标准：

- 输出 `[OK] trace 校验通过`，`check_trace` 显示事件数 = 10；
- `pytest` 全部 passed，无失败无报错；
- 本轮验证生成的 `trace.jsonl`、`seed-workbook.xlsx` 属于测试数据，**不提交**；
- 验证完成恢复基线：

```powershell
git restore --source=HEAD -- demo/output/trace.jsonl demo/seed-workbook.xlsx
```

（等价写法：`git checkout HEAD -- demo/output/trace.jsonl demo/seed-workbook.xlsx`）

⚠️回滚预案：验证出现校验失败时，停止提交；`git diff` 对比改动，定位哪一处优化
破坏了行为；回退对应代码改动，重跑全套验证直到全部通过。

### 9.5.2 两阶段提交策略（trace 必须来自 OBS 录制那次）

| 阶段 | 操作内容 | git 提交内容 | 关键约束 |
| --- | --- | --- | --- |
| 阶段一：代码优化提交 | 代码优化、文档更新、计划更新 | `src/`、`docs/`、`README.md`、`pyproject.toml`、`.gitignore`；**不含** trace、`seed-workbook.xlsx` | 验证后 `git restore` 恢复 trace 与 xlsx 基线；提交前 `git status` 检查待提交文件列表 |
| 阶段二：录制产出提交 | `init_seed` → OBS 录制完整会话 | 仅 `demo/output/trace.jsonl`、`demo/seed-workbook.xlsx` | 独立 commit、独立 push；trace 必须来自本次 OBS 录制会话 |

⚠️ 本轮优化验证会生成新 trace，**不得**作为初赛提交的最终 trace；
正式提交的 trace 是 OBS 录视频那一次产出。

### 9.5.3 OBS 录制会话完整操作（第二阶段，含判定与回滚）

> 录制全程原则：录制开始后，除脚本内命令以外，不再执行任何 gx 相关写操作，
> 防止向 trace 追加事件、导致轨迹与视频对不上。

```powershell
# 步骤0 重建干净虚拟环境（推荐，规避旧 venv 损坏）
python -m venv .venv
# Windows 激活：.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 步骤1 重置种子，清空 trace，恢复干净初始状态
python demo/init_seed.py
# ✅判定：执行完毕，demo/output/trace.jsonl 为全新初始化状态

# 打开 OBS，开启录制
# 步骤2 打印帮助（只读，已验证不写 trace）
python -m gx --help
# ✅判定：完整输出 CLI 帮助表格，出现提示符后再敲下一行

# 步骤3 运行完整 demo，生成最终交付 trace
python demo/run_demo.py
# ✅判定：脚本完整跑完 9 个环节，无报错

# 步骤4 trace 校验（只读）
python tools/check_trace.py
# ✅判定：输出 [OK] trace 校验通过，事件总数 = 10 条

# 🛑 立刻停止 OBS 录制！
# ❌ 录制结束之后禁止执行：任何 gx 命令、run_demo.py、init_seed.py，
#    防止追加 / 覆盖 trace

# 步骤5 提交最终轨迹（独立 commit）
git add demo/output/trace.jsonl demo/seed-workbook.xlsx
git commit -m "final preliminary demo trace from obs record"
git push origin main
```

**录制失败回滚预案**：录制过程报错或输错命令时，直接停止 OBS，
**丢弃本次录制视频（不要保存）**；执行 `python demo/init_seed.py` 重置；
OBS 重新开启录制，从头再来。

**核对要点**：

- `check_trace.py` 输出的「共 N 条事件」应为 **10 条**：
  prompt / tool_call / member.add / pr.create / permission.deny /
  pr.merge 失败 / pr.approve / workflow.run / pr.merge 成功 / human_intervene；
- 拿到 Raw 链接后在无痕浏览器打开，确认是纯 JSONL 文本，不是 GitHub 网页，
  且没有混杂历史旧事件；
- 不要重跑 `run_demo.py`、不要执行 `gx member add` 等写命令，
  它们都会向默认 trace 路径追加事件。

> 环境提示：若 `python` 不在 PATH（本机曾出现该情况），先用实际可用的
> Python 3.11-3.14 解释器路径创建 venv，再执行上述流程。

### 9.5.4 提交后校验（容易忽略，提交后必做）

- GitHub 网页打开仓库，切换 main 分支，确认两笔 commit（代码优化 + 录制轨迹）都在线；
- 打开 `demo/output/trace.jsonl`，点击 **Raw**，复制链接；
- 无痕浏览器打开该 Raw 链接：
  - ✅正确：直接展示纯 JSONL 文本，一共 10 行事件；
  - ❌错误：打开的是 GitHub 网页界面 / 事件行数不是 10 / 存在大量历史旧事件；
- 把仓库主页链接、trace Raw 链接保存到记事本；
- OBS 视频剪辑完成（3-5 分钟），上传公开平台（Bilibili / YouTube / 抖音等），
  复制分享链接；
- 三个链接全部准备完毕，再填写初赛表单。

## 9.6 风险清单与规避

| 风险场景 | 现象 | 规避手段 |
| --- | --- | --- |
| 阶段一验证产生 trace，误提交到第一笔 commit | trace 混入代码优化提交 | 验证后 `git restore` 恢复 trace、xlsx 基线；提交前 `git status` 检查待提交文件列表 |
| 录制完成后手误执行写命令 | trace 事件多于 10 条，视频与轨迹不一致 | 录制停止后不再运行写命令；提交前核对 trace 行数 = 10 |
| 用普通网页链接代替 Raw 链接填入表单 | 评审拿到网页 HTML，不是原始 trace 文本 | 必须无痕浏览器打开 Raw 链接确认 |
| 旧虚拟环境损坏 | `check_env` 报版本不匹配、随机异常 | 录制前重建全新 venv |
| `init_seed` 忘记执行 | trace 叠加历史事件，行数远大于 10 | 录制第一步强制执行 `init_seed`，`check_trace` 看事件总数 |
| 录制中途报错 / 输错命令仍继续 | 视频与轨迹错位，无法对齐 | 丢弃本次录制，`init_seed` 重置后从头录制 |
